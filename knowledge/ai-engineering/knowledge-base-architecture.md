# Knowledge Base Architecture

## The problem

This repository exists to be an agent's external long-term engineering memory. That imposes
constraints a documentation site or an awesome-list does not have:

```text
CONTEXT IS SCARCE       An agent cannot read 400 files to answer one question. Structure must let
                        it load what is relevant and skip what is not, without a human curating
                        the selection each time.
TRUST MUST BE CARRIED   A retrieved fact with no provenance is indistinguishable from a
                        hallucinated one. Grading has to live with the content, not in a separate
                        document nobody loads.
IT MUST BE MACHINE-CHECKED  Anything a human has to remember to do will eventually not be done.
                        Schemas, validators and CI are the enforcement layer; conventions in prose
                        are the fallback, not the mechanism.
IT MUST AGE             Content that cannot expire cannot be trusted. Freshness has to be
                        structural — a field on every artifact, checked by a script.
```

## Structural decisions

Six decisions shape everything else. Each was made deliberately and is reversible only with an ADR.

```text
1. PROGRESSIVE DISCLOSURE.  A skill body stays under a token budget; the detail it needs lives in
   references/ next to it, loaded when the step is reached. This is why five skills carry a
   references/ subdirectory — the budget was enforced, and the content moved out rather than being
   deleted.

2. FRONTMATTER IS THE CONTRACT.  Every governed markdown file opens with YAML validated against a
   JSON Schema with additionalProperties: false. Unknown keys fail the build. This is what makes
   the corpus queryable instead of merely readable.

3. METADATA BENEATH CARDS.  Machine-readable JSON (metadata/*.json) is the source of truth;
   human-readable cards (repositories/**/*.md) are generated from it and never hand-edited. Editing
   a card is overwritten on the next run — the correct action is to edit curation.json or the data.

4. INDEXES ARE DERIVED.  indexes/ contains 13 files generated by build_index.py from the registries
   extract_registries.py pulls out of frontmatter. No index is written by hand, so no index can
   drift from the content it describes.

5. STATUS OVERRIDES SCORE.  Numeric grading and lifecycle classification are separate layers. An
   archived repository with a high score is not an adoption candidate. See repository-status.md.

6. HARD OVERRIDES BEFORE SCORING.  license: null, archived: true, leaked provenance and
   unresolvable sources are applied before any weighted average, because a sufficiently high
   adoption score must never be able to outvote a legal or safety defect.
```

## The four layers

```text
LAYER 1 — CONTENT (hand-written, schema-validated)
  skills/36 · agents/12 · workflows/10 · knowledge/ · patterns/ · prompts/ · evaluations/
  anti-patterns/ · failure-modes/ · gotchas/ · decision-records/ · experimental/
  Each file: YAML frontmatter (validated) + markdown body (budgeted).

LAYER 2 — METADATA (machine-generated, scored)
  metadata/repositories.json (414 records) · metadata/sources-papers.json ·
  metadata/unverified-papers.json · metadata/pending-paper-candidates.json
  Built by scripts/update/fetch_github_metadata.py from the GitHub API plus curation.json.

LAYER 3 — DERIVED VIEWS (regenerated, never hand-edited)
  repositories/<category>/<owner>--<name>.md (418 cards) · indexes/*.md (13 files) ·
  README statistics table
  Built by scripts/generate-index/{extract_registries,build_index,generate_repository_cards,
  update_readme_stats}.py

LAYER 4 — ENFORCEMENT
  schemas/ (17 JSON Schemas) · scripts/validate/ (frontmatter, json, links, policy) ·
  scripts/deduplicate/dedupe.py · scripts/update/check_staleness.py ·
  .github/workflows/kb-ci.yml (6 jobs) · Makefile
```

The dependency direction is strictly downward: content → metadata → derived views. A change in
layer 1 or 2 regenerates layer 3; nothing flows back up. That is what makes the corpus safe to
regenerate wholesale.

## The retrieval path

What an agent actually does with this repository, from task to answer:

```text
1. ENTER THROUGH AGENTS.md      The policy file states the three standing rules (research before
                                code, don't reinvent the wheel, proven pattern first) and the
                                reading order for the indexes.

2. PICK THE WORKFLOW            workflows/ is the coarse-grained entry point: 10 multi-stage
                                processes, each with stages, exit gates and the skills/agents they
                                invoke. A workflow names its dependencies, so nothing has to be
                                discovered by search.

3. LOAD ONLY THE NAMED SKILLS   A skill body is budgeted to be loadable. Its references/ are not
                                loaded until the step that needs them is reached.

4. CONSULT THE KNOWLEDGE LAYER  For domain facts rather than procedures. Every article carries
                                claim_type, evidence_level, verified_at, expires_at and sources.

5. CHECK STATUS BEFORE ADOPTING For any repository recommendation: read the card's tier, status
                                and license_risk before treating the score as an endorsement.

6. RESOLVE CONFLICTS BY RULE    Two sources disagree → precedence is primary > official >
                                independent corroboration > community. The conflict is recorded,
                                not silently resolved. See knowledge/research/source-conflict-
                                case-study.md for a worked example.

7. RECORD WHAT WAS LEARNED      Anything durable discovered during the task becomes a knowledge
                                article, a gotcha or a decision record, with sources — which is
                                how the corpus grows without losing its grading discipline.
```

## What was rejected

```text
✗ A flat collection of markdown notes.   Readable, unqueryable, ungradeable. Every claim would
                                         carry the same implicit confidence as every other.
✗ An awesome-list of links.              Links without scores and dates are a bookmark folder. The
                                         reader inherits the curator's judgement with no way to
                                         inspect it.
✗ One giant document per topic.          Defeats progressive disclosure; an agent would load 40k
                                         tokens to use 2k.
✗ Embeddings as the primary retrieval mechanism.  No vector store is committed here. Retrieval is
                                         structural — directory layout, frontmatter fields, indexes
                                         — because it is inspectable, diffable, reproducible and
                                         requires no infrastructure. An embedding layer can be built
                                         on top of the frontmatter; the reverse is not true.
✗ Hand-maintained indexes.               They drift. Every index here is generated, so drift is
                                         impossible rather than merely discouraged.
✗ Scoring from reputation or familiarity.  Every score component reads a field returned by an API
                                         or a cited document. See source-scoring.md.
```
